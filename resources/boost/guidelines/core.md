# Internet Guru

This application is built by Internet Guru on top of its own `internetguru/*` packages. These rules apply on top of the Laravel Boost guidelines and win where the two differ.

## Boundaries

- Branches, versions and releases are managed by the Flow script (`internetguru/flow`). Edit `VERSION` only on `dev`, when a breaking change requires a new major version (see `ig-flow`). Never change version headings in `CHANGELOG.md` or tags by hand, and never merge between key branches yourself. Before starting a task, run `flow --pull` to bring in coworkers' changes, then check the current branch: if it is the one you would recommend for the task, work there without asking; ask only when you would recommend a different branch or the choice is ambiguous. A fix for the release candidate is committed on `staging`. A commit on `staging` is always merged into `dev` (`flow --yes --conform --pull`) before it is pushed. Run `flow` or `git push` only after the user agrees to that step. Activate `ig-flow`.
- Before deciding anything based on the current branch, or reporting on it, check it again with `git branch --show-current`. The developer may switch branches by hand, or a tool may switch them in the background, so the branch you saw earlier may no longer be current.
- Never edit, copy into, or symlink anything under `vendor/`, and do not switch a package to a path repository. A change to an `internetguru/*` package belongs in that package's own repository. It runs in the application only while the developer's `docker-compose.vendor.yml` mounts that package into the containers; activate `ig-package-development`.
- Before building a new feature, first consider whether it belongs in a package rather than the application: anything other Internet Guru applications would use, or that extends what an `internetguru/*` package already does, goes to `laravel-common` or the fitting existing package. Propose a new package only as a last resort, for a self-contained area no package covers. Say where you would put it and why, and let the user decide before writing code; activate `ig-package-development`.
- Do not build frontend assets (`npm run build`, `npm run dev`); the developer runs Vite.
- `Dockerfile`, `docker-compose*.yml` and the server-managed `.env` values are generated by docker-ansible and are not committed. Do not hand-edit them; propose the change for docker-ansible instead.

## Working with the user

- **Discuss first.** Before changing files, look into the task, then present the conceptual parts (the approach, the design, the trade-offs) with the options and the one you recommend. Change files only once they are clear and agreed, so no better solution is left undiscussed. Minor slips, such as a typo, need no discussion: fix them or leave them.
- **Review.** For a bigger task, or whenever the user asks for a review, get advice on the approach and a review of the result from the strongest model available (for example Claude Fable), through a subagent where the agent supports one. A review covers the code and, when views, styles or scripts changed, the UI. Give the reviewer the code and the screens rather than your conclusions, and discuss its findings with the user before acting on them.
- **Follow-ups.** When a task is done, end with the follow-ups it revealed, most significant first: what else to do, fix, check or test. Name the most severe one as the one to do next. Leave Flow steps such as pushing or releasing out of it; see Boundaries. A follow-up the user postpones goes into Considerations.

## Considerations

- A change worth considering that is not carried out now goes into the `## Considerations` section of the application's `README.md`, so it is not lost. Examples: a change for an `internetguru/*` package, a docker-ansible or server change, a check with a third party, a follow-up refactoring.
- Write one bullet per item: where the change belongs, what to do, why, and what in the application to update or remove once it is done.
- When the section grows past about five items, move it to `CONSIDERATIONS.md` in the application root and link that file from the README.
- Remove an item once it is done or dropped.

## Data

- Never run hand-written SQL, `migrate:fresh`, `db:seed` or any other write against a database that is not the local development or test one. Data changes ship as migrations.
- Never commit `.env` files, database dumps (`*.sql`, `*.sqlite`) or credentials, and use only test keys for payment gateways.

## Writing

- Write English in American spelling (en_US): `color`, `behavior`, `center`, `gray`, `analyze`. This covers replies, plans, comments, docs, changelog entries, commit messages and `lang/en`. Fix any British spelling you come across in such text. Leave identifiers that other code or packages rely on, such as config keys, CSS classes or translation keys, alone.
- In a plan, open each section with a short plain-language summary of what changes and why, readable without knowing the code. Files, functions and other technical details come after it.

## Code style

- Code documents itself through names and small methods. Write a comment only where the code cannot say why, and keep it to one line. Never leave commented-out code, and never keep generated docblocks such as "Display the specified resource." PHPDoc is only for types the signature cannot express, such as array shapes and generics.
- Follow the Boost PHP rules for new and changed code. Leave untouched code alone: no drive-by reformatting, renaming or modernizing.

## Testing

The full suite takes minutes, so running it is not the agent's job.

- **When to add a test:** only for behavior that could break unnoticed, such as logic, permissions, validation, stored data, or a Livewire or Alpine interaction. A purely visual change (styles, icons, wording, spacing, layout) gets no new test. This overrides Boost's rule to test every change.
- **While working:** run only the test file or `--filter` that covers the change, e.g. `composer run artisan -- test --compact --no-ansi tests/Feature/OrderDetailTest.php`. That takes seconds. Run tests for most changes, except minor edits; when in doubt, run them.
- **Browser tests:** behavior that only works in the browser (Livewire actions, Alpine, modals, keyboard handling) gets a Pest browser test in `tests/Browser`; the rest stays in feature tests. Select elements by `@testid` and add a `data-testid` to the view when one is missing, build data with factories, and end each test with `assertNoJavascriptErrors()`. Run it like any test file; on a failure, read the screenshot in `tests/Browser/Screenshots`. Activate `ig-local-environment` when the browser does not start or a page loads without its styles or scripts.
- **Before a commit:** add or update the tests the change needs in the same commit, then run the affected test files once, e.g. every `tests/Feature/Order*Test.php` after touching orders.
- **Full suite:** CI runs it only on the production branch (`main` or `master`), so on other branches the developer runs `composer run test:all`. That command migrates the test database once and runs in parallel when Paratest is installed; `test:php` runs only the PHP tests and `test:browser` only the browser tests. If the user asks for the full suite, run `composer run test:all -- --compact --no-ansi` in the background and report only the summary and the failures.
- **Output:** always pass `--compact --no-ansi`. Never `--colors=never`: `artisan test` adds its own `--colors` in a terminal, and Pest exits with an error on the duplicate. Add `--bail` (Pest) or `--stop-on-failure` (PHPUnit) when chasing a failure. Read failures from the end of the output.
- **Many identical failures point to the setup, not the code.** One cause failing dozens of tests, such as "Vite manifest not found" or a missing database, is a harness problem. Report it instead of debugging each test.

## Before finishing

- Run `vendor/bin/pint --dirty --format agent`, the affected test files (see Testing), and `vendor/bin/phpstan analyse` (Larastan, level 8, `app/`). Fix new PHPStan errors instead of adding them to `ignoreErrors` or the baseline. If the project has no `phpstan.neon` yet, say so; do not install Larastan without approval.
- After changing translations, run `./validate_trans.sh` and `./langdiff.sh` if the project has them.

## Frontend

- Reuse the `x-ig::` package components, use Bootstrap utilities and Sass partials instead of inline `style`, size things in relative units (`rem`, `em`, `%`, `vw`/`vh`, `thin` borders) and never `px`, never shrink or fade text to make it look secondary (no text below `1rem`, WCAG AA contrast), keep behavior in global Alpine components rather than `<script>` tags, and register every Font Awesome icon in `resources/js/fontawesome-init.js`. Activate `ig-frontend` before touching `resources/views`, `resources/sass` or `resources/js`.

## Changelog

- Every change a user or package consumer would notice gets a `CHANGELOG.md` entry, in the same commit as the change. Which section it goes to depends on the branch: `[Unreleased]` on `dev`, feature and hotfix branches, and the current release candidate on `staging` (see `ig-flow`). Follow [Keep a Changelog](https://keepachangelog.com/en/2.0.0/), keep each entry brief and human readable, and activate `ig-changelog` before writing one.

## Commits

- Commit only when asked, on the current branch. The subject is one short sentence in the imperative saying what changed, with no prefix or trailing period, e.g. `Show the status above the heading`.

## Translations

- Applications are multilingual (`lang/cs`, `lang/en`, sometimes more). Never hardcode user-facing text, and add every new key to all locales the project has. Lang files are flat: dotted keys such as `'checkout.alert' => '…'`, never nested arrays. Activate `ig-translations` when touching `lang/` or adding user-facing strings.

## Local environment

- The application runs in Docker (service `laravel`, code mounted at `/app`), deployed locally by docker-ansible. `internetguru/laravel-scripts` adds composer scripts that run inside it: `composer run artisan <command>`, `composer run test:php`, `composer run test:browser`, `composer run test:all`, `composer run bash`, `composer run migrate:fresh`. Activate `ig-local-environment` when tests or Artisan fail to run.
