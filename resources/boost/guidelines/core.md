# Internet Guru

This application is built by Internet Guru on top of its own `internetguru/*` packages. These rules apply on top of the Laravel Boost guidelines and win where the two differ.

## Boundaries

- Branches, versions and releases are managed by the Flow script (`internetguru/flow`). Never change `VERSION`, version headings in `CHANGELOG.md` or tags by hand, and never merge between key branches yourself. Before starting a task, run `flow --pull` to bring in coworkers' changes, then ask whether to work on the current branch or create a feature or hotfix branch. After committing, ask whether to push or release. Run `flow` or `git push` only after the user agrees to that step. Activate `ig-flow`.
- Never edit, copy into, or symlink anything under `vendor/`, and do not switch a package to a path repository. A change to an `internetguru/*` package belongs in that package's own repository. It runs in the application only while the developer's `docker-compose.vendor.yml` mounts that package into the containers; activate `ig-package-development`.
- Do not build frontend assets (`npm run build`, `npm run dev`); the developer runs Vite.
- `Dockerfile`, `docker-compose*.yml` and the server-managed `.env` values are generated by docker-ansible and are not committed. Do not hand-edit them; propose the change for docker-ansible instead.

## Data

- Never run hand-written SQL, `migrate:fresh`, `db:seed` or any other write against a database that is not the local development or test one. Data changes ship as migrations.
- Never commit `.env` files, database dumps (`*.sql`, `*.sqlite`) or credentials, and use only test keys for payment gateways.

## Code style

- Code documents itself through names and small methods. Write a comment only where the code cannot say why, and keep it to one line. Never restate the code, never leave commented-out code, and never keep generated docblocks such as "Display the specified resource." PHPDoc is only for types the signature cannot express, such as array shapes and generics.
- Follow the Boost PHP rules for new and changed code. Leave untouched code alone: no drive-by reformatting, renaming or modernizing.

## Testing

The full suite takes minutes, so running it is not the agent's job.

- **While working:** run only the test file or `--filter` that covers the change, e.g. `composer artisan test --compact --colors=never tests/Feature/OrderDetailTest.php`. That takes seconds. Never run the full suite mid-task, and don't rerun tests after every edit.
- **Before a commit:** add or update the tests for the change in the same commit, then run the affected test files once, e.g. every `tests/Feature/Order*Test.php` after touching orders.
- **Full suite:** CI runs it on push, or the developer runs `composer test:php`. That command migrates the test database once and runs in parallel when Paratest is installed. If the user asks for the full suite, run `composer test:php -- --compact --colors=never` in the background and report only the summary and the failures.
- **Output:** always pass `--compact --colors=never`. Add `--bail` (Pest) or `--stop-on-failure` (PHPUnit) when chasing a failure. Read failures from the end of the output, not the whole log.
- **Many identical failures point to the setup, not the code.** One cause failing dozens of tests, such as "Vite manifest not found" or a missing database, is a harness problem. Report it instead of debugging each test.

## Before finishing

- Run `vendor/bin/pint --dirty --format agent`, the affected test files (see Testing), and `vendor/bin/phpstan analyse` (Larastan, level 8, `app/`). Fix new PHPStan errors instead of adding them to `ignoreErrors` or the baseline. If the project has no `phpstan.neon` yet, say so; do not install Larastan without approval.
- After changing translations, run `./validate_trans.sh` and `./langdiff.sh` if the project has them.

## Frontend

- Reuse the `x-ig::` package components, use Bootstrap utilities and Sass partials instead of inline `style`, keep behaviour in global Alpine components rather than `<script>` tags, and register every Font Awesome icon in `resources/js/fontawesome-init.js`. Activate `ig-frontend` before touching `resources/views`, `resources/sass` or `resources/js`.

## Changelog

- Every change a user or package consumer would notice gets a `CHANGELOG.md` entry, in the same commit as the change. Which section it goes to depends on the branch: `[Unreleased]` on `dev`, the current release candidate on `staging`, and Flow's release prompt on feature and hotfix branches (see `ig-flow`). Follow [Keep a Changelog](https://keepachangelog.com/en/2.0.0/), keep each entry brief and human readable, and activate `ig-changelog` before writing one.

## Commits

- Commit only when asked, on the current branch, then ask about pushing or releasing (see `ig-flow`). The subject is one short sentence in the imperative saying what changed, with no prefix or trailing period, e.g. `Show the status above the heading`.

## Translations

- Applications are multilingual (`lang/cs`, `lang/en`, sometimes more). Never hardcode user-facing text, and add every new key to all locales the project has. Lang files are flat: dotted keys such as `'checkout.alert' => '…'`, never nested arrays. Activate `ig-translations` when touching `lang/` or adding user-facing strings.

## Local environment

- The application runs in Docker (service `laravel`, code mounted at `/app`), deployed locally by docker-ansible. `internetguru/laravel-scripts` adds composer scripts that run inside it: `composer artisan <command>`, `composer test:php`, `composer bash`, `composer migrate:fresh`, `composer test:e2e`. Activate `ig-local-environment` when tests or Artisan fail to run.
